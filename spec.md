# Spacebox — Technical Specification

Version: `0.1.5` (`Engine/Application.cs` → `Application.Version`)

## 1. Overview

Spacebox is a single-player voxel survival game set in an asteroid belt, with an experimental client/server multiplayer mode. It runs on a custom C# engine built on OpenTK. Game content (blocks, items, recipes, generation) is data-driven through JSON "GameSets", and code plugins are loaded as DLLs.

| | |
|---|---|
| Language / runtime | C# / .NET 8 (`net8.0`; `SpaceServerUI` is `net8.0-windows`) |
| Graphics | OpenGL 3.3 core, forward-compatible context (OpenTK 4.8.2) |
| UI | ImGui.NET 1.91 (game UI and debug tools), SkiaSharp (engine-side 2D) |
| Audio | OpenAL (via OpenTK) + NVorbis (`.ogg`) |
| Networking | LiteNetLib 1.3.1 (UDP) in `Engine/Networking` |
| Save format | NBT (SharpNBT) for world entities, JSON for metadata/player |
| Archives | SharpCompress (`.zip` / `.rar` GameSets) |
| Tests / benchmarks | xUnit 2.5, BenchmarkDotNet 0.14 |
| Platforms | Windows, Linux, macOS (`win-x64`, `linux-x64`, `osx-x64`) |

## 3. Engine

### 3.1 Application lifecycle

`Program.Main` creates a 1280×720 `SpaceboxWindow`, centred on the primary monitor. `SpaceboxWindow` extends the abstract `EngineWindow` (an OpenTK `GameWindow`), which drives the loop and exposes these hooks:

| Hook | Use in Spacebox |
|---|---|
| `OnRegisterScenes` | Registers all scenes with `SceneManager` |
| `OnGameLoad` | Sets the icon and loads `MenuScene` |
| `OnSetupInput` | Input actions (`InputPro`) |
| `OnSetupPostProcessing` | Adds post effects (vignette enabled) |
| `OnLoadImGui`, `OnRenderGameGUI`, `OnUpdateInput`, `OnPostRender` | ImGui setup, GUI, input, screenshot (F12) |

### 3.2 Scenes and scene graph

- `Scene` (abstract, inherits `Node3D`) implements `LoadContent` / `UnloadContent` / `Update` / `Render`.
- `SceneManager.Register<T>()` then `SceneManager.Load<T>()`; `ErrorScene` is shown when a scene fails to load.
- Game scenes: `LogoScene`, `MenuScene`, `LocalSpaceScene` (all game modes, built on `BaseSpaceScene`), `ServerMessageScene`, `PlaygroundScene`. Engine tool scene: `ParticleSystemEditor`.
- `Node3D` + `Transform3D` form the hierarchy; behaviour is attached as `Component`s.

### 3.3 Rendering

- Shaders are single `.glsl` files with `--Vert` / `--Frag` sections. They support `#include` (shared code in `Resources/Shaders/includes/`: `core.fs`, `fog.glsl`) and are loaded by path without the extension, e.g. `Resources.Load<Shader>("Resources/Shaders/block", true)`.
- Shared per-frame uniforms (camera position, fog density, …) go through `GlobalUniforms` / `UniformBuffer`; GL state is tracked in `GLState`.
- Camera-relative rendering is available (toggled by a console command) to keep precision across the large world.
- Culling: `CameraFrustum`, `BHVCuller`, octrees (`Octree<T>`, `PointOctree`).
- Lighting (`Engine/Light`): directional, point and spot lights from a `LightPool`, managed by `LightSystem`. Voxel light and emission are computed separately on the game side.
- Post-processing (`PostProcessManager`): SSAO, vignette, color grading and camera feed (in this order; camera feed = security-camera look while `ShipPilot.IsUsingCamera`: barrel distortion, chromatic aberration, tint, scanlines, rolling band, 24 Hz grain, vignette, toggled each frame by `CameraFeedController`, REC overlay `CameraFeedOverlayUI`; hotbar and health/power/oxygen bars are hidden in camera view via `HudVisibility.ShowPlayerHud`; color grading = gamma brightness, contrast, saturation and film grain in one pass, `IsRequired` so it works with post processing off, skipped while neutral); black-and-white, edge detection, normal view and depth view are also available. Effects run in list order (`AddEffect`/`InsertEffect`); the last result is presented with the passthrough shader.
- G-buffer (`SceneRenderer`): `ColorAttachment0` RGBA8 color, `ColorAttachment1` RGBA8 with `rgb` = view-space normal × 0.5 + 0.5 and `a` = AO mask (0 none: sky, emissive, blended or cleared pixels; 0.5 view-model drawn with its own projection; 1 world), `DepthComponent24` texture. Attachment 1 is written only by materials with `MaterialBase.WritesGBuffer` in Opaque/Cutout mode (`GLState.GBufferWrite` masks it otherwise); shaders write it through `includes/gbuffer.glsl` (`writeGBuffer`). Writers: `block`, `movingBlock`, `itemModel` (held item: mask 0.5, sets `ViewModelProjection` each frame), `textured` (`TextureMaterial` with the default shader: mobs, players, NPCs, dropped items). `colored` (`ColorMaterial`: lines, debug shapes) and `blockPreview` (build preview) write mask 0 (`writeGBufferNone`) so they never inherit the AO of what is behind them.
- SSAO (`Engine/PostProcessing/Ssao`, shaders `PostProcessing/ssao*.glsl`): `SsaoSettings` (quality, strength 0-2, smoothness 0-1 scales the preset blur radius ×0-2, grain 0-1 and grain size 1-8 px (static screen-space dots: each grain cell is a fixed grey dot with probability proportional to the occlusion, so dots are dense near edges and thin out, mean brightness kept; blended with the smooth AO by grain), view-model strength 0.4 faded out on faces turned to the camera, radius 0.75 blocks (0.1-4), view-model radius 0.04, bias, fade 48-96 m) and `SsaoPreset` per quality (Low: 1/2 resolution, 8 samples, blur 2; Medium: 1/2, 16, blur 3; High: full, 16, blur 4). Passes: linear depth at AO resolution (`R32F`, negative for the view-model, 0 = skip) → normal-oriented hemisphere sampling with a 4×4 rotation noise, samples of another mask ignored, depth-scaled bias, distance fade → separable bilateral blur (`R8`) → composite: depth-aware 4-tap upsample, `color × (1 − (1 − ao) × strength)`. Console `ssao_debug` shows the raw AO. The effect ignores the global post-processing switch; quality Off disables it.
- Other renderers: skybox / procedural skybox, particles, sprites/billboards, lines/axes/bounding-box debug draws, planets/atmosphere/sun/water shaders.

- Render scale: `EngineWindow.RenderScale` renders the scene FBO at a fraction of the window size; post processing stretches it to the window, the GUI stays at full resolution. `EngineWindow.PostProcessingEnabled` skips all effects.

## 4. World Model

### 4.1 Spatial hierarchy

```
World (Component, singleton)        octree of Sectors, 8192 sectors per axis
 └─ Sector (8192³ blocks)           SpaceEntity list + lazily generated placeholders
     └─ SpaceEntity (asteroid/ship) 16³ chunks = 512³ blocks max
         └─ Chunk (32³ blocks)      Block[32,32,32], mesh, lighting
             └─ Block
```

- `World` loads sectors around the player and unloads distant ones, checked periodically.
- Each `Sector` places entities from the generator as `NotGeneratedEntity` placeholders. A placeholder becomes a full `SpaceEntity` when the player comes close. Destroyed entities are tracked by name in `EntitiesDestroyed`.
- All levels implement `ISpaceStructure`.

### 4.2 Block

`Block` packs its core state into one 64-bit field (37 bits used):

| Bits | Field | Range |
|---|---|---|
| 0–11 | BlockId | 12 bits → max 4096 block types |
| 12–14 | Direction | `Down, Up, Left, Right, Back, Forward` (default `Up`) |
| 15–22 | Mass | byte |
| 23–30 | Durability | byte |
| 31–34 | Flags | `Transparent, Air, Light, EnableEmission` |
| 35–36 | Rotation | `None, Right, Half, Left` |

It also has non-packed properties: `Color`, `LightColor` (`Color3Byte`), `LightLevel` and an `OnDestroy` callback.

Behaviour subclasses are created by `BlockFactory` from the JSON `Type` string (case-insensitive):

| `Type` | Class |
|---|---|
| `block` | `Block` |
| `mineral` | `MineralBlock` |
| `interactive` | `InteractiveBlock` |
| `storage` | `StorageBlock` (uses `StorageBlockData`) |
| `craftingtable` | `CraftingTableBlock` |
| `furnace`, `crusher` | resource processing blocks |
| `disassembler` | electrical consumer (JSON `Disassembler.Power`, default 40); 4×2 input and 4×2 output slots; disassembles items by `disassembly.json` (see Disassembly), speed scales with `Efficiency`. Saved via `DisassemblerSerializer` (`input_slots`, `output_slots`, `progress`; reads old `input_data`/`output_data`) |
| `analyzer`, `radar` | utility blocks |
| `generator`, `consumer`, `cable` | electrical network (`ElectricalManager`). Generators read JSON `Generator { Power }` (default 50, up to 1600) and an optional `Explosive` block (same fields as bombs): such a generator explodes when projectile damage brings a cell to 0 durability (`Chunk.DamageBlock` detonates instead of removing) or another blast breaks it (nuclear power blocks: radius 3, low penetration, max damage below what a full titanium set absorbs, checked by `DefaultReactorBalanceTests`); generation/consumption rates are 16-bit. In multi-cell electrical blocks only the origin cell generates/consumes, other cells only transfer (`ConfigureAsMultiblockPart`) |
| `gravity` | gravity generator (`GravityGeneratorBlock`, consumer). JSON `Gravity { Radius, MinRadius, MaxRadius, Strength, MinStrength, MaxStrength, Power, StrengthPowerFactor, MaxRoomCells, Presets[{Name, Strength}] }` (32, 4, 512, 9.81, 0.5, 30, 200, 0.25, 200000, Moon/Mars/Earth/Jupiter). Consumption = Power × radius/Radius × (1 + StrengthPowerFactor × (strength/Strength − 1)), 0 when switched off. `GravityGeneratorUI` sets radius, strength (presets), on/off and "only inside closed rooms" (flood fill from the block, `SealedRoomFill`/`GravityRoom`, leaks past the radius or `MaxRoomCells` count as open). Per-block settings saved as NBT `gravity_generator_data` (radius, strength, enabled, inside_only; omitted when default). Fade = min(6, radius/4). While powered it pulls toward the block's bottom side; registered in `GravityField` via `IEntityBlockListener`. Fields fade over the last 6 blocks; overlapping fields blend their directions by distance. Inside a field the player uses `GravityWalker` (capsule 1.6 m, eye at 1.5 m, walk/jump, auto-upright); drops and `SphereBody` objects fall |
| `dnareconstructor` | DNA reconstructor (`DnaReconstructorBlock`, consumer). JSON `DnaReconstructor { DnaItem, Power, ReconstructionTime }` (`dna_sample`, 50, 5). One DNA slot (`DnaReconstructorUI`), saved as NBT `dna_reconstructor_data`. Registered in `DnaReconstructorRegistry`; after death the player can respawn at the nearest powered one with DNA (uses 1 sample, `DnaReconstructionScreen` animation, free cell found by `SafeSpawnFinder`) |
| `explosive` | Bomb (`ExplosiveBlock`, `IProjectileReactive`). JSON `Explosive { Radius, Penetration, Damage, DamageFalloff, PushStrength, PushRadiusMultiplier, ChainDelay, DropBlocks, DestroyStorageItems }` (DropBlocks false: destroyed blocks drop nothing; DestroyStorageItems false: storages and machines still drop their contents). Detonates when hit by a projectile; `ExplosionSystem` (`World.Explosions`, max 2 per frame) casts Fibonacci rays (`BlastRayCaster`, penetration is spent on block durability), removes plain blocks in bulk with merged drops and special blocks (storages, electrical, doors, multiblocks) through the normal path (`ExplosionBlockBreaker`), chains other bombs, pushes the player/drops/bodies within Radius × PushRadiusMultiplier and damages within Radius (`ExplosionForces`, survival only for the player) |
| `door` | sliding multi-cell door (`Game/Generation/Doors`). JSON `Door`: `MoveDirection` (model direction, e.g. `Right`), `Speed` (blocks/s), `OpenTime` (s), `AutoClose`. Opening/closing moves the real cells between the doorway and the slide area (oxygen, collisions and saves follow); the slide is animated by a separate mesh while the cells are hidden from the chunk mesh (`Block.IsMeshHidden`, bit 49, mass still counted); the mesh is lit with the voxel light of the air around the door at its start and end position, blended by progress (`BlockLightSampler.AverageAroundCells`), and drawn with `Resources/Shaders/movingBlock` (same lighting as `block.glsl`: ambient + voxel light, point and spot lights, no directional light), so it keeps the block colour while moving. The area a door does not occupy is reserved (no blocks can be placed). While sliding, the door's cells do not collide or get hit by raycasts; instead the moving door box collides (`DoorSystem.IntersectsMovingDoor`) and pushes the player, physics bodies and resting drops along the slide direction (crushing the player if the push would end inside a wall); raycasts (projectiles, thrown drops, tools) hit the moving door box (`DoorSystem.RaycastMovingDoors`) and resolve to a real door cell. Saved via `DoorSerializer` (`is_open`, `auto_close_timer`) |
| `oxygengenerator` | electrical consumer (20); needs water in its tank; fills a sealed room with air (`Game/Generation/Oxygen`); if all air around it leaks (outside or an open room) it stops (`IsOutside`, no water use) and its window says so, and starts again once a side is sealed. Crafting: basic machine, 4 aluminium panels, microchip, 2 glass. JSON `OxygenGenerator`: `WaterItem`, `TankCapacity` (30), `WaterConsumeInterval` (120 s), `WaterFillInterval` (1 s). Saved via `OxygenGeneratorSerializer` (`water`, `consume_progress`, `slot_data`) |

### 4.3 Meshing and lighting

- `MeshGenerator` builds chunk meshes and reads neighbouring chunks for faces at chunk borders. `ChunkLODMeshGenerator` builds reduced-detail meshes for distant chunks.
- Block vertex layout (`block.glsl`): position `vec3`, UV `vec2`, colour `vec3`, normal `vec3`, AO `vec2`.
- Multi-cell blocks: `Size {x,y,z}` in `blocks.json` (1..16 per axis, model axes: x width, y height, z depth, front = `FrontDirection`). Every cell stores the same block id/direction/rotation plus its model offset (`Block.MultiblockOffset`, bits 37–48); the cell with offset 0 is the origin. `MultiblockLayout` maps model offsets to entity cells for the block orientation. Placement checks all cells (`SpaceEntity.CanPlaceStructure`), removing any cell removes the structure (`SpaceEntity.RemoveStructure`). Face textures larger than one tile (`BlockSize`) span the face; tile-sized textures repeat per cell. Saved per chunk in `multiblock_offsets` (index, packed offset). When an entity is loaded, `MultiblockRepair` checks every structure before the chunks are built: an origin whose other cells are missing (the block got bigger in a GameSet update) is completed if those cells are free and loaded, otherwise the block is removed (cell left empty, no drop); part cells without a matching origin are removed. So `Size` can grow without a save-format step.
- Custom block geometry (`Game/Generation/Shapes`): `Model` in `blocks.json` names a shape. It resolves to a code-built geometry registered in `BlockGeometryLibrary` (`BlockGeometryBuilder`, built-in `slab`) or to an OBJ file in the GameSet (`Models/Blocks/<name>.obj`, or a GameSet-relative path with extension; the active GameSet first, then `Default`). OBJ units are blocks, the model's bottom (min Y, centred in X/Z) is the side that rests on a block; model UVs (0..1) map onto the block's face texture chosen by each vertex normal. `BlockShape` precomputes poses for every direction/rotation: the model's up follows `Block.Direction`/`Rotation`. Placement (`BlockPlacementHelper`) points the model's up along the normal of the clicked face (rotation none). In empty space the model's up follows the player's up (snapped to an axis) and the rotate key turns it: up, away from the player, down, towards the player, so its bottom rests on the clicked block; when that neighbour is not a full solid block the model is centred in the cell. The build preview draws the same pose (`BlockShapePreviewMesh`). Shaped blocks set `Block.HasCustomShape` (bit 50) and are meshed from the model (no face culling or AO); they never hide neighbour faces, let light and air through, and do not support other shaped blocks. Collisions, sphere physics and raycasts use the pose's bounding box (`BlockCollision`, `BoxMath`); ship hulls skip them, but other ships' hull samples still hit them. Default: the 8 `lights` blocks are wall torches (`Models/Blocks/torch.obj`, 0.4×0.8×0.4; its UVs use the centre 16×32 px of side textures and 16×16 px of cap textures). Textures `Blocks/Lights/torch<Color>.png` (iron-palette metal bands at top and bottom, a full-width light window in the middle made from the old light texture that connects around the corners, emission only on the window) and `torchMetal.png` (caps) are generated by `Assets/Models/torch_textures.py`.
- Reserved areas: block data implementing `IReservedAreaBlockData` (doors: slide area; thrusters: nozzle cells from `ThrusterNozzle`) must be empty and unreserved to place the block (`SpaceEntity.IsReservedAreaFree`, also on the server through `TryPlaceBlock`). Placed thrusters reserve their nozzle cells in `SpaceEntity.Reservations` (`CellReservations`, registered from `IEntityBlockListener`), so `IsCellReserved` blocks building there. The build preview outlines the area (cyan, red when blocked; the block preview is hidden when it cannot be placed).
- Rotation: each `SpaceEntity` has an `Orientation` (quaternion, pivot = `PositionWorld`). Procedural asteroids get a random orientation from their seed; it is saved in the entity's `rotation_*` tags. Voxel code works in *entity space* (world space as if unrotated: `chunk.PositionWorld`, `BoundingBox`, `GeometryBoundingBox`, `CenterOfMass`); `ToEntitySpace`/`ToWorldSpace` convert at the boundaries (rendering, culling, raycasts, collisions, oxygen, effects, build preview).
- Oxygen: each `SpaceEntity` has an `OxygenSystem`. Air is not a block: breathable cells are bit masks per chunk, rebuilt by a flood fill from every oxygen generator over empty blocks (radius 32). Reaching the radius limit or a missing chunk counts as a leak (no air). Recalculated only when a generator is placed/removed, a chunk is added/removed, or a block changes next to a reached cell. Not saved; rebuilt on load.
- `AOVoxels` computes per-vertex ambient occlusion (0fps method, `AOShading`): each face corner checks its two side cells and the corner cell in front of the face; both sides solid = level 0, otherwise 3 − solid count; brightness = (level + 1) / 4. Quads are split along the diagonal with the lower brightness sum (`AOShading.ShouldFlip`). Mesh snapshots read edge and corner neighbour chunks through `SpaceEntity.TryGetChunk`, and editing a border cell remeshes every chunk it touches (`ChunkBorder`), so AO and smooth light are continuous across chunk edges. `LightManager` propagates block light per RGB channel (each channel keeps the strongest value decayed by 0.8 per block, so overlapping lights blend instead of meeting in a hard line; a relight clears and refills only the cells within light reach (18 blocks) of the chunk, seeded by its light sources and the lit cells just outside that region, so light from farther chunks survives); the mesher lights each vertex by averaging the light of the up to 4 air cells around that corner (smooth lighting, diagonal corners ignored when both sides are solid); changing emission or light requires rebuilding the chunk mesh.
- Textures are packed by `Engine.Graphics.Atlas.TextureAtlas` (skyline packing, any texture sizes, power-of-two atlas, optional padding, extra layers such as `emission`). Textures can be added from folders, files, `Texture2D` or pixels at any time; the atlas rebuilds lazily and `AtlasRegion` UVs update in place. `GameAtlasFactory` builds the blocks atlas (GameSet `Blocks/` + `Resources/Textures/Blocks`, e.g. `LOD.png`) and the items atlas (GameSet `Items/` + `Resources/Textures/Items` creative tools + small UI images from `Resources/Textures/UI` + generated isometric block icons). UI draws icons and slots with `AtlasSprite` (one texture for a whole inventory).

### 4.4 Procedural generation

- Driven by `GameSets/<set>/Generation/generator.json`. Default: 1250–2500 asteroids per sector, at least 128 blocks apart, rejection sampling, biome-map noise frequency `0.001`.
- `BiomeGenerator` / `BiomesMap` choose a biome per region (`asteroid_field`, `dense_cluster`, `debug`). Biomes reference asteroid presets (`light`, `medium`, `heavy`, `asteroid_icy`, `cheese`).
- Asteroid voxels come from `AsteroidVoxelDataGenerator`, using `Spacebox/Generation/` helpers: `NoiseGenerator`, `PerlinWorms`, `InternalCavities`, `AsteroidOreGenerator`, `MaskContainer`, `SectorPointProvider`, `SeedHelper`. `PerlinWorms` builds each node's worm paths once (cached, up to 1024 nodes, cleared on world unload) and carves only the path points inside the padded chunk. Chunk meshes come back as pooled arrays with counts (`MeshData.VertexCount`/`IndexCount`, returned with `Release`) and are uploaded into the chunk's existing GPU buffers (`Mesh.Update`).
- Loot tables (`Generation/Loot`) and structure definitions (`abandoned_ship`, `alien_base`, `ruins`) are data files.
- Generation runs on the worker pool. Results are handed back to the GL thread through `MainThreadDispatcher`; all OpenGL calls must happen on the main thread.

## 5. Gameplay Systems

- **Tutorial** (`Game/Tutorial/`, design in `tutorial-design.md`): JSON tutorials in `GameSets/<set>/Tutorials/*.json` (chapters → steps → tasks, item icons, `{key:action}`/`{item:id}` tokens, rewards, game-mode filters, skippable steps). `TutorialRunner` runs one tutorial for the local player; progress is saved in the player JSON (`Tutorial`, optional). Tasks are created by type in `TutorialTaskFactory` (press, hold, look, move, place_block, destroy_block, pickup, have_item, craft, process, use_item, use_block, equip, open_ui, select_hotbar, toggle, stat, pilot, bind_ship_part, ship_camera, ship_travel, enter_gravity, create_waypoint, wait, all_of, any_of) and read game state through `ITutorialContext` and `PlayerActivity` events. UI: compact panel in the top-right (`TutorialUI`, collapse with `tutorial` = J, finished tasks green and crossed out, toasts for steps/chapters), pause menu → Tutorial (skip, stop, resume, restart), the welcome screen has a "Play the tutorial" checkbox, new multiplayer players get a start prompt. Headless servers do not load tutorials.
- **Player:** `Astronaut` → `LocalAstronaut` (local player) and `RemoteAstronaut` (network players). Includes inertia-based 6-DoF movement (`InertiaController`, `MovementMode`), camera/item sway, flashlight, equipment, mood, statistics, death handling (`DeathCase`). Statistics (`PlayerStatistics`, saved in the player JSON): `PlayerStatsTracker` adds play time every frame and path length per frame through `DistanceTracker` (steps under 1 mm ignored, steps faster than 1000 m/s treated as teleports, reset on `SetPosition`/`Teleport`, not counted while dead, frozen, spectating or viewing through a ship camera; ship travel also counts into `DistanceInShips`), max speed, visited sectors and asteroids (within 64 blocks, checked every second); sessions count once per world load; deaths per cause and consumables per item id (max 64 keys, rest in `Other`). Old saves load (integer distance and minutes are migrated).
- **Game modes:** `SurvivalMode`, `CreativeMode`, `SpectatorMode`, `CameraMode` (all `GameModeBase`).
- **Interactions:** `InteractionHandler` switches between modes such as place block, destroy block (survival/creative), shoot, consume item, eraser and camera point.
- **Block placement range:** a placed block joins the nearest entity only if that entity has a solid block within `SpaceEntity.BuildAttachDistance` (16 blocks, spherical) of the target cell (`SpaceEntity.IsWithinBuildRange`, `BlockProximity`); otherwise it starts a new entity (`EntityCreationNetwork.PlaceNewEntity`). Multiblock structures check their origin cell. The range does not depend on the entity's mass or size.
- **Items** (`Type` in `items.json`): base `item`, `drill` (tier for blocks, `Damage` per second to bodies such as the spacer and mobs (default 1), power usage (per destroyed block, and per second while drilling a body in survival), range, colour), `weapon` (projectiles from `ProjectilesPool`, defined by `ProjectileJSON`), `consumable`, `equipment` (`Slot`: Helmet/Shoulders/Chest/Arms/Legs/Boots/PowerGenerator/Flashlight/Scanner, `Health`/`Power` bonuses to max stats; `ExplosionProtection` (percent 0-100, default 0) summed over the worn pieces (`PlayerEquipment.ExplosionProtection`, capped at 75%) reduces explosion damage (`ArmorProtection.Apply` in `ExplosionForces`, each client applies it to its own player); Default full sets: aluminium 10%, iron 30%, titanium 50% (helmet 1 : chest 3 : shoulders 2 : arms 1 : legs 2 : boots 1 parts of a set); optional `Flashlight` { `Intensity`, `Range`, `InnerAngle`, `OuterAngle` } and `Radar` { `Range`, `ShowMass` } settings; stack size 1). Flashlight items set the player's spot light (`EquipmentFlashlightBinder`, synced to other players); the flashlight works only with one equipped or, if the slot is empty, held in the hand (`LocalAstronaut.ActiveFlashlightItem`; survival and creative). Radar items gate markers: asteroid/ship markers (`Tag.TagCategory.Entity`) are drawn only with a radar and within its range, player waypoints always, the mass only if `ShowMass`; only spectator uses `RadarSettings.Unlimited`. Equipment in `ItemsOnStart` goes straight into empty equipment slots; player saves without `EquipmentSlots` (older saves) get it once on load. Shift-click (`storage_item_quick_transfer`) in the inventory or hotbar and right click (`use`) with equipment in hand equip it, swapping with the equipped item (`PlayerEquipment.TryEquip`, `InteractionEquipItem`). Equipment can define `ArmorModel` and `ArmorTexture` (paths inside the GameSet, e.g. `Models/Armor/armor_chest.obj`, `Models/Armor/armor_iron.png`); when both files exist, the piece is drawn on local and remote astronauts (`ArmorRenderer`, `ArmorLibrary`; equipped item ids are synced per slot by `AstronautNetwork`), otherwise nothing is drawn. The Default armor meshes copy the astronaut parts one texel (1/32) outside the body and use the skin UV layout, so one mesh per slot works with every 64×64 armor texture (generator: `Assets/Models/armor_build.py`). Equipment window (`EquipmentUI`, next to the inventory): compact, placed beside the inventory and moved right of the crafting window when they would overlap: armor slots in body order (helmet, chest, legs, boots on the left; shoulders, arms on the right), a device column (power generator, flashlight, radar) on the far right, and in the middle `PlayerPreview`: an offscreen render (`RenderTexture` + `OrbitViewCamera`, own copy of the scene skybox) of the astronaut in the session skin colour (Yellow in single player) with the equipped armor (`ArmorRenderer`) and the held item or block (`HeldItemModels`, shared with `HandItemVisualizer`); lit with the world ambient light; drag rotates, double click resets, dropping an item slot on it equips the item (`InventoryUIHelper.AcceptSlotDrop` + `PlayerEquipment.TryEquip`, swapping with the worn piece). Default tiers: aluminium/iron/titanium flashlights, radars (1000 m, +mass, 1200 m + mass) and power generators (+10/+20/+30).. Max stack is limited to 255.
- **Inventory and crafting:** `Game/Inventory`, `crafting.json`, `recipes.json`. Crafting categories have an optional `Row` (1 or 2) for the two rows of category buttons (`CraftingCategoryLayout`; categories without a row fill the shorter row). Default rows: Blocks, Lights, Windows, Resources, Other, Ships / Drills, Tools, Weapons, Equipment, Items, Consumables. Inside a category items come first and blocks after them, each in load order (`CraftingCategoryOrder`). JSON `Description` texts are short and contain no numbers (checked by `DefaultDescriptionsTests`); parameters appear in tooltips: blocks through `IBlockTooltip` on their block data (generators, explosives, pipes, doors, gravity, oxygen and DNA machines, disassembler, ship parts) plus machine speed (`Efficiency`), items through `IItemTooltip` (repair tool) and the drill, weapon, equipment (flashlight beam, radar range) and consumable sections of `InventoryUIHelper.ShowTooltip`.
- **Repair tool** (`Type: "repair_tool"`, `RepairToolItem`: `RepairPerSecond`, `PowerPerSecond`, `Range`; `InteractionRepair`): aiming at a block shows its name, a durability bar and `No repair needed` or `Durability N% (current/max)` under the crosshair (`RepairTargetUI`); multi-cell blocks are measured over all their cells (`RepairTarget`, `DurabilityTally`: summed durability, the weakest cell is repaired first); holding the primary action raises durability up to the block data's maximum per cell and uses power in survival. Repairs are sent as `BlockRepairMessage` (entity, cell, block id, amount) through `WorldEditNetwork` and applied with `BlockDamage.Repair` on every peer.
- **Disassembly** (`Game/Disassembly`, `DisassemblerBlock`, `DisassemblerUI`): the powered disassembler takes the first input item that has a recipe, enough count and room in the output, and turns it into its parts (server only; progress pauses without power). `DisassemblyRecipes` resolves a recipe per item through rules in order: `disassembly.json` entry (`Disabled`, or explicit `Products` + optional `InputQuantity`, default 1), legacy `disassembler` recipes in `recipes.json`, then a derived recipe: from every crafting blueprint and processing recipe (furnace, crusher, …) that makes the item, `ingredient × ReturnPercent / 100` rounded down per crafted batch (input = the recipe's product quantity unless `InputQuantity` is set), virtual `$` ingredients skipped, the cheapest result chosen; if any recipe would give nothing (e.g. a single ingredient of 1 at 50 %), the item can't be disassembled. Duration: entry `DurationSec`, else the processing recipe's time, else `DefaultDurationSec`. Input slots only accept disassemblable items; output slots accept nothing from players. On load `DisassemblyBalanceAudit` warns about explicit recipes that give more of an item than the cheapest crafting recipe costs. Pipes insert only disassemblable items and take from the output slots (`DisassemblerEndpoint`). Multiplayer: processing runs only on the server; the container state (status, progress, required ticks, current item, server power state, completion counter) reaches remote clients through `ContainerServer` snapshots, and remote clients play the finish sound when the counter changes. `DisassemblerUI` is laid out in fractions of the screen height (text scaled with `SetWindowFontScale`), so it keeps its size and place at any resolution; progress is an arrow between the grids.
- **Physics:** voxel ray hits and collisions in `VoxelPhysics`. Damage goes to `IDamageable` objects registered with `World`.
- **Effects:** drops (`DropManager`), block destruction and mining effects, particles.
- **Item pipes** (`Type: "pipe"`, `PipeBlock`, `Game/Logistics`): a powered block (`Pipe.Power`, default 5) with one item slot and a filter slot. Every `Pipe.TransferInterval` seconds (default 1, server only, `PipeRegistry`) it pushes its item to one of its output sides (`Pipe.OutputSides`: block-local `Up`/`Left`/`Right`/`Forward`/`Back`, default all five; `item_pipe_straight` uses only `Up`; round robin) and pulls one item from its input sides (`Pipe.InputSides`, default `Down`, round robin; `item_pipe_merger` takes from `Down`, `Left`, `Right` and outputs `Up`; output sides never include an input side), only items that an output can take and that match the filter. Neighbours are `IItemTransferEndpoint`s resolved by `ItemTransferEndpoints`: storages (take anything, insert anywhere), processing machines (take only the output slot, insert only recipe ingredients into the input slot and restart the machine), the disassembler (`DisassemblerEndpoint`), other containers (insert only into filtered slots, e.g. water, DNA) and pipes (accept only from a pipe on one of their input sides). The tooltip lists inputs, outputs, rate and power. Pipe slots are saved (`pipe_data`). The filter slot is `ItemSlot.IsManualOnly` (skipped by quick transfer and auto fill) and has a tooltip hint (`ItemSlot.Hint`).
- **Mobs** (`Game/Mobs`): data-driven (`Mobs/*.json` in the GameSet → `MobDefinition` in `GameAssets.Mobs`). `Mob` is a `Node3D` with a `SphereBody`; mouth = model +Z, it faces its movement, food or target. AI runs only on the server: `MobSenses` (sight range, field of view, hearing range, line of sight through blocks, alert on damage, forget time), `MobLocomotion` (path requests through `MobSystem.Paths`, waypoint steering, repath, stuck/unreachable flags), brain from `MobBrainFactory` by `Behaviour` (a `StateMachine<MobContext>` of reusable states in `Mobs/States`). Navigation uses `MobNavigationGrid`, anchored to the nearest asteroid's block grid (entity-local cells, also rotated entities) or to world cells in empty space. `MobSpawner` (server) spawns around players by the `Spawn` rules; mobs farther than `DespawnDistance` from every player are despawned; mobs are not saved. `MobSystem` (scene component) owns the scheduler, spawner, despawning and the live mob list.
- **Mineral parasite** (`behaviour: parasite`): 50 HP, bite 8–20 every 1.2 s in 1.6 m, sees 14 m (140° FOV, hears 4 m). Rests until hungry, then forages (search food → approach → eat 3 s with block-dust particles → rest; wander if nothing found) on natural blocks (all asteroid layer/vein blocks, `NaturalBlocks`). Hunger fills in `MealIntervalMin`–`MealIntervalMax` (60–600 s) depending on the nearest player (≤ 24 m: fastest, ≥ 96 m: never eats), ±30 % per mob, so few chunk rebuilds happen. Chases and bites visible survival players, 10 % of parasites flee instead. Drills hurt it with their `Damage` per second (weapons are much better). Spawns only in unlit air cells next to natural blocks, max 1 per chunk, 24 total, 16–48 m from a player. Drops come from the loot table named by `Loot` (file name in `Generation/Loot/`, `mineral_parasite.json`: rocks, cobaltite, ice).
- **Mob spawner items** (`Type: "mob_spawner"`, `Mob`: mob id, `UseCooldown`): RMB spawns the mob at the aimed surface or 3 m ahead (consumed in survival); `mineral_parasite_spawner`. Console: `mob <id> [count]`, `mob list`, `mob clear` (server only).
- **Ships** (`Game/Ships`, see `ships-design.md`): every dynamic (player-built) `SpaceEntity` has a `ShipBody` (rigid body: mass and diagonal inertia from its blocks, force/impulse at points, damping only without thrust, `MaxSpeed`/`MaxAngularSpeed` caps, settings in the GameSet `ships.json` → `ShipPhysicsSettings`). Moving uses `SpaceEntity.SetPose` (shifts chunk world caches and the sector octree). Ship blocks register with the entity's `ShipControlSystem` through `IEntityBlockListener`: `thruster` (`Thruster` { `Force`, `Power`, `NozzleLength` (blocks kept free in front of the nozzle face, 0..16, default 0; Default: weak 1, others 2) }, pushes away from its front face), `shipconsole` (`Console` { `Buttons` (groups, max 16), `Power`, `Weapons`, `Flight` }), `cannon` (`Cannon` { `Projectile`, `ReloadTime` ms, `ShotSound`, `BarrelLength`, `AimCone`, `TurnSpeed`, `Power` }), `shipcamera` (`ShipCamera` { `Power` }). Using a powered console seats the player (`ShipPilot`); the inventory key opens `ShipConsoleUI` (keys per colour group, "Bind blocks", leave), `ShipBindingTool` binds parts by looking at them while the player moves freely (LMB / mouse wheel step through groups that have a key, camera toggles; RMB returns to the seat; outlines via `ShipOutlineRenderer`, key labels on bound blocks). Thrusters bound to a key are manual only and are skipped by automatic flight. A bound powered camera renders the view from the camera block through a separate `ShipViewCamera` (`Camera.Main` while viewing, block mesh hidden) while the player stays at the console: the body is visible there, synced to other players at the seat and can be damaged there; opening it turns the view to where the bound cannons aim (camera front otherwise). Non-flight consoles let Q/E roll the view. Flight consoles fire thrusters automatically (`AutoFlight`: translation/rotation classes by thrust direction and torque in the console frame, mouse steering with a PD controller unless Alt is held, sprint brakes; mouse steering only fires sets of unbound thrusters whose forces cancel out (`AutoFlight.SelectBalanced`, net force at most 20% of their total), so it never pushes the ship by itself — a single engine fires only for its movement key). Cannons aim at the point under the pilot's crosshair (`ConsoleCommand.AimPointLocal`, raycast ignoring the own ship) inside their cone, rotating around the centre of their base face (`CannonBlock.PivotLocal`, from size and front direction); while aimed they are drawn as a separate rotating model (`CannonTurretRenderer`, block cells hidden like moving doors). They shoot through the normal projectile/combat path (`ShipWeapons`), adding the ship's point velocity; their projectiles never hit their own ship, and a cannon holds fire (keeping its reload) while its line of fire from the muzzle hits its own ship or its pilot within 512 blocks (`CannonLineOfFire`, server side). Thrusters push away from their nozzle (model top, placed facing the player). Collisions (`ShipCollider`, `ShipHull`, `ShipContactSolver`): a 3×3 grid of samples on every exposed hull face (0.05 inside the surface) is tested against blocks of nearby entities, and the hull samples of nearby ships against the own blocks, in substeps (≤ 0.35 blocks per substep), contacts revert the substep and apply an impulse (`CollisionBounce`, friction 0.3); asteroids have infinite mass. Players standing near a ship are carried with it (`ShipRider`). Thruster flames: `ShipThrusterEffects` (owned by `World`).

### 6.1 GameSets

A GameSet is a folder (or a `.zip` / `.rar` archive, extracted by `GameSetsUnpacker`) under `GameSets/`:

```
GameSets/Default/
  config.json      ModId, ModName, Author, Version, BlockSize (no longer limits texture sizes), OxygenConsumeInterval (s per 1 oxygen, default 10), Dependencies, ItemsOnStart

                   Textures, Sounds, Drop, DropQuantity, Model, …)
  items.json       item definitions
  crafting.json    crafting categories/blueprints
  recipes.json     processing recipes (furnace, crusher, …); crusher recycling never returns more metal dust than the item's crafting cost in ingots (checked by `DefaultCrusherRecipesTests`)
  disassembly.json optional: DefaultReturnPercent (50), DefaultDurationSec (10), Items [ { Item, Disabled, ReturnPercent, DurationSec, InputQuantity, Products [ { Item, Quantity } ] } ]; without the file every item uses the defaults
  ships.json       optional ship physics: MaxSpeed, MaxAngularSpeed, LinearDamping, AngularDamping, LinearSnap, AngularSnap, MaxStep, BoardDistance, LeaveDistance, CollisionBounce
```

## 7. Persistence

Worlds are stored in `<app dir>/Worlds/<world>/`:

| File | Format | Content |
|---|---|---|
| `world.json` | JSON | `WorldInfo`: name, seed, game version, GameSet, … |
| `player.json` | JSON | Player state (`PlayerSaveLoadManager`): position, `SpawnPoint` (first join position, optional; falls back to position), health/power/oxygen, `InventorySlots`, `PanelSlots`, `EquipmentSlots` (optional) |
| `Sectors/<sector>/<entity>.entity` | NBT | Modified `SpaceEntity` data (`NBTHelper.SpaceEntityToTag`). Procedural asteroids set `only_changed_chunks` = 1 and store only edited/previously saved chunks plus `removed_chunks` (packed chunk indices); unchanged chunks are regenerated from the seed on load. A chunk with `needs_generation` = 1 was created before its natural content was generated and gets it merged in later. Files without the flag (older saves, player-built entities) contain all chunks. |

- Entity files are independent of the sector that wrote them: the position is stored relative to the sector folder the file is in, so a `.entity` file can be copied into any sector folder of any world. Procedural asteroids also store `asteroid_type` (asteroid id of the GameSet) and `asteroid_radius`, so their untouched chunks regenerate anywhere (seed = entity id). Entities that move into another sector are transferred (`EntitySectorTracker`, `Sector.ReleaseEntity` / `AcceptEntity`); the origin sector suppresses a procedural id that left it, the old file is deleted when the entity is saved in its new folder (`SpaceEntity.SavedSectorIndex`), duplicates of an id (file copied twice) are ignored with a warning, and modified sector data is saved when a sector unloads.
- Moving entities also save `velocity` / `angular_velocity` (float lists, missing = at rest); ship consoles save their bindings as `ship_console_data` (byte array: group count, weapons flag, keys, camera cell, bound cells with groups).
- Only modified entities are saved. When an entity unloads, it goes into a concurrent cache in `WorldPersistenceManager`. The cache is written to disk on a background worker (`SaveAllCacheToDiskAsync`) or immediately (`SaveAllCacheToDiskNow`). Saving is available from the pause menu (Esc).
- **World upgrades** (`Game/Versioning/`, used by `VersionConverter`, the menu's convert dialog and the dedicated server on start):
  - Support window: the oldest convertible version is 0.1.2 (`WorldUpgradeRegistry.DefaultMinimumSupportedVersion`); 0.1.2 converts directly to 0.1.5 (`Steps/Upgrade_0_1_2_To_0_1_5`, which replaces the removed `cobalt_crystal` item with `cobalt_ingot`). Statuses: `Ok`, `UpToDate`, `TooOld`, `Newer`, `NoPath`, `InvalidVersion`, `UnsupportedFormat`, `Failed`.
  - `WorldUpgradeRegistry` holds one `IWorldUpgradeStep` per version (`FromVersion` → `ToVersion`, unique, always newer). `WorldUpgrader` builds the full chain, runs the first step's `Check` (the 0.1.2 step refuses older formats saved under the 0.1.2 label, detected by `WorldFormatProbe`: legacy `worldX`/`indexX`/int palettes and `world_x` world-space positions), zips the world folder to `Worlds/_backups/<folder>_<version>_<time>.zip`, applies the steps in order (version updated after each) and restores the backup if a step throws. Nothing is changed or backed up when a check fails.
  - Operations in `WorldUpgradeContext`: `RenameBlock` (block palettes; the block's item too), `RenameItem` (item palettes, player `InventorySlots`/`PanelSlots`/`EquipmentSlots` `ItemID`, `drop.json` `ItemId`), `RemoveBlock` (palette entry → air or a replacement, stored items cleared), `RemoveItem`, and editors `EditChunks`, `EditEntities`, `EditSectors`, `EditPlayers`, `EditDrops`, `EditJson`/`EditJsonFiles`. NBT files are written only when changed (`NbtFileEditor`). Counters give the result summary.
  - After the steps `WorldValidator` lists block/item ids that the world's GameSet (`GameSetIdIndex`, read from `blocks.json`/`items.json`) does not define; they are shown as warnings.
  - Tests: `Spacebox.Tests/Versioning/` (`WorldFixtureBuilder` writes worlds in the real format, `WorldInspector` reads them back); every world in `Spacebox.Tests/Fixtures/Worlds/<version>/` must upgrade to the current version without warnings.
- **Waypoints** (`Game/Waypoints/`): window on `waypoints` (M): list with color, name and distance, add at the player position, rename, color palette or custom color, show/hide, delete. Waypoints are static tags saved in the world's `tags.json`; a multiplayer client keeps them in its own scratch folder, so only that player sees them. Waypoints are always drawn (radar only gates asteroid/ship markers and mass). Block magnet moved to N.
- **Player spawn** (`generator.json` `PlayerSpawn` { `MinAsteroidRadius`, `ExcludedAsteroids` }, `PlayerSpawnRules`): new players spawn at a random allowed asteroid; without one, the largest not excluded (then the largest). Default: radius ≥ 24, not `asteroid_icy`.

## 8. Multiplayer

The game is always client and server at once (Godot-style shared world). Engine networking lives in `Engine/Networking`, game networking in `Spacebox/Network`. The old `SpaceNetwork`/`SpaceServer`/`SpaceServerUI`/`CommonLibrary` projects are deprecated and no longer referenced by the game.

- **Modes** (`NetworkManager.Mode`, `GameSession.Mode`): `Offline` (singleplayer = server without a socket), `Host` (same world, listening), `Client` (remote), `DedicatedServer` (`Spacebox.exe --server`, or `start-server.bat` / `start-server.sh` next to the executable; hidden window that never captures the cursor, `serverconfig.json`, all log messages are written to the terminal with time and colour (on Windows the process attaches to the calling console or opens its own, `TerminalConsole`), stdin commands `say`, `players`, `kick`, `save`, `stop`). The dedicated server runs headless (`Application.EnableHeadless()` in `Program`): no audio device, no rendering or ImGui drawing, textures/atlas images are registered as 1x1 placeholders without decoding, shaders are not compiled, meshes are not uploaded, chunk meshing only computes mass and bounds, no LODs, skybox, music, dust or block icons. Singleplayer can be opened to the network from the pause menu ("Open to network", port 7777). `--connect host:port --name <name> [--hidden]` joins directly.
- **Server config** (`serverconfig.json`, `ServerConfig`): `ServerName`, `Description`, `IconFile` (PNG or JPEG next to the executable, default `server-icon.png`; a missing file falls back to the same name with `.png`/`.jpg`/`.jpeg`, up to 256 KB, square 64-128 px recommended), `LanDiscovery`, `WhitelistEnabled` + `Whitelist` (names allowed to join, default off), `RegistrationEnabled` (accounts with passwords, default off), `WorldName`, `Seed`, `ModId`, `Port`, `MaxPlayers`, `GameMode`, `AutoSaveInterval` (seconds, default 300, 0 disables, minimum 10; hosts autosave every 300 s; every save prints `[Server] Autosave: world ... saved` to the terminal), `UpdateRate` (server loop rate, default 30, 10-240; client graphics settings such as VSync and the FPS cap are not used by the server), `DashboardEnabled` (default true), `DashboardPort` (TCP, 0 = same number as `Port`), `DashboardCertificateFile` / `DashboardCertificateKeyFile` / `DashboardCertificatePassword` (optional HTTPS, see below), `PublicAddress` (name or public IP for automatic HTTPS), `HttpsAutomatic` (default true), `HttpsChallengePort` (default 80), `DuckDnsToken` + `DuckDnsUpdateIp` (default true), `CloudflareApiToken`, `LetsEncryptEmail`, `LetsEncryptStaging` (default false); the older `DuckDnsDomain` still works as `PublicAddress` = `<name>.duckdns.org`. The server writes the file back on start, so missing settings appear with their defaults.
- **Web dashboard** (`Network/Dashboard/`, page files in `Resources/Dashboard/`: `index.html`, `style.css`, `app.js`, no libraries; the pixel font is served from `Resources/Fonts/StarPixel.ttf`): started by `DedicatedServer.Launch` when `DashboardEnabled`, served by the engine's dependency-free `Engine/Web/MiniHttpServer` (raw TCP, one IPv4 and one IPv6-only listener, 32 connections, 15 s per request, 512 KB bodies, `Connection: close`) at `http://<server>:<port>/dashboard` (TCP; the game itself is UDP, so the same port number works). Security: on start without an admin the server writes a random one-time key to `dashboard/setup-key.txt` next to the executable and logs its path; registering the single admin needs that key, the key file is then deleted. The password is stored as PBKDF2-SHA256 (`dashboard/admin.json`, salt + derived key, 100000 iterations, min 8 characters); delete the file to register again. Sessions are random 256-bit tokens in an `HttpOnly; SameSite=Strict; Path=/dashboard` cookie (12 h, sliding). Every request except reading needs the header `X-Spacebox-Dashboard: 1` (blocks cross-site forms, no CORS answers). 5 failed logins or setup keys per address lock it for 5 minutes. Responses carry CSP (`'self'` only), `X-Frame-Options: DENY`, `nosniff`, `no-referrer`; static files are resolved inside `Resources/Dashboard` only. HTTPS (optional, `DashboardCertificate`): a PEM certificate + key (for example Let's Encrypt `fullchain.pem` + `privkey.pem` for a DuckDNS name) or a PFX with password; relative paths start at the executable. The server peeks at the first byte of every connection and wraps TLS handshakes (`0x16`) in `SslStream` (TLS 1.2/1.3), so HTTP and HTTPS share the port (`MiniHttpServer.CertificateProvider`, `PrefixedStream`). With a certificate, plain HTTP is only accepted from loopback/private/link-local addresses (`NetworkAddresses.IsLocal`); other GET requests are redirected with 301 to `https://<Host><path>`, other methods get 403 (`DashboardHttpsPolicy`); HTTPS responses send HSTS and login cookies get `Secure`. The files are re-read when their write time changes (checked once a minute), so renewals need no restart; a warning is logged 14 days before expiry; broken or missing files leave the dashboard HTTP only. Without a certificate the dashboard is plain HTTP: use it on a trusted network. Automatic HTTPS (`AutoCertificateService`, used when `PublicAddress` is set, `HttpsAutomatic` is on and no certificate file is configured; `HttpsMethodSelector` picks the method): `*.duckdns.org` + `DuckDnsToken` → DNS-01 via the DuckDNS TXT record (30 s wait); `CloudflareApiToken` → DNS-01 via the Cloudflare API (`CloudflareDnsClient`: zone lookup from the longest name down, `_acme-challenge` TXT record created and deleted, 15 s wait); anything else, including a bare public IP → HTTP-01 (`HttpChallengeSolver` opens `HttpsChallengePort` only during the check, or answers through the dashboard server when it uses the same port; HTTPS redirects skip `/.well-known/acme-challenge/`). IP addresses use the `ip` identifier and the Let's Encrypt `shortlived` profile (about 6 days). Local addresses (loopback, private ranges, `localhost`) are refused without contacting Let's Encrypt. With a DuckDNS name and token the server also sends its public IP to DuckDNS every 5 minutes (`DuckDnsClient`), independent of HTTPS. The engine ACME client (`Engine/Web/Acme/AcmeClient`, RFC 8555, ES256 JWS account key `dashboard/certificates/account.pem`, challenges through `IAcmeChallengeSolver`, RSA 2048 certificate key) writes `dashboard/certificates/<address>/fullchain.pem` + `privkey.pem`; the service checks every 12 h, renews when a third of the lifetime is left, logs failures with a hint (token, DNS, port 80), retries after 1 h and makes `DashboardCertificate` reload at once. Tested against a fake ACME server (signatures, nonces, DNS and HTTP checks) and against the real Let's Encrypt staging API (account and order accepted). The overview shows the HTTPS state. Player-facing guide: `Spacebox Server Guide.pdf` in the game folder (source `Documentation/server-guide/server-guide.html`, printed with `build-pdf.ps1` through Edge/Chrome, published with the game). Setup guide: `Documentation/dashboard-public-access.md` (port forwarding, CGNAT, NAT loopback, acme.sh / Posh-ACME with the DuckDNS DNS challenge). Admin actions are logged as `[Dashboard] <admin>: ...`. Features (`Modules/`: `AuthModule`, `ServerModule`, `PlayersModule`, `ModerationModule`, `ConsoleModule`, `StaticFilesModule`, all game calls marshalled to the main thread with `Engine.MainThread.Run`): overview with players, uptime, CPU (process time / cores), RAM (working set), game ticks per second, update time and world size, 6-minute charts (`DashboardMetrics`, a sample every 2 s), server info, broadcast chat, save / restart / stop (`ServerRestart`: restart starts the same executable with the same arguments plus `--wait-pid <pid>` and quits; the new process waits until the old one exited), settings (name, description, max players, LAN visibility, autosave, frame rate; applied live: advertisement, `MaxPeers`, `FrameLimiter`), server icon upload (PNG/JPEG, 256 KB), online players (ping, address, position, alive, muted) and all saved players with kick, mute, ban, player detail (health, power, oxygen, position, equipment, hotbar, inventory with item icons from the GameSet textures, statistics; from the last client sync when online, else the save file), banned names and addresses, muted players, whitelist on/off with add/remove (`NetworkSession.ReloadAccessSettings`), live console (`Debug.MessageLogged` → `DashboardLog`, last 1000 lines) with command input, history and completion, and the dashboard password change.
- **Server query** (`Engine/Networking/Query`): servers answer LiteNetLib unconnected messages on the game port without a connection (`NetworkManager.Query` = `ServerQueryResponder`, filled by `ServerAdvertiser` from `NetworkSession`). `InfoRequest` → `InfoResponse` with a payload (game `ServerStatus`: instance id, name, description, version, GameSet, world, game mode, players, max players, dedicated flag; max 1100 bytes) plus the icon hash/size; the icon is fetched in 1 KB chunks (`BlobRequest`/`BlobChunk`, FNV-64 hash, lost chunks re-requested). Broadcasts to the port find LAN servers (ignored when `LanDiscovery` is false). Hosted singleplayer worlds answer with the world name and no icon.
- **Accounts** (`Network/Auth`, only when `RegistrationEnabled`): after the join checks (version, ban, whitelist, unique name) the server sends `AuthChallengeMessage` (registered or not, salt, PBKDF2 iterations, random nonce). The client derives a key = PBKDF2-SHA256(password, salt, 100000) and answers `AuthResponseMessage` with HMAC-SHA256(key, nonce); for a new name it also sends the key once to create the account. The password itself never leaves the client. Accounts are stored per world in `accounts.json` (name, salt, derived key, iterations); 3 wrong passwords or 180 s without an answer end the join. `AuthPromptWindow` (menu) asks for the password or a new one twice; "Save password" stores only the derived key per server and name in `Multiplayer/credentials.json` (written after a successful join, removed when it stops working), next joins send it automatically. Console command `unregister <name>` deletes an account.
- **Server list** (`MultiplayerWindow`, `ServerBrowser`, `ServerQueryClient` on its own socket): saved servers from `client.json` (`Name`, `Description`, `IP`, `Port`, `IconHash`) and servers found in the local network (broadcast to 255.255.255.255 and to the subnet broadcast address of every network adapter, `127.0.0.1`, and the remembered LAN servers in `client.json` `LocalServers` (`ip:port`, newest first, max 16) pinged directly first; deduplicated by instance id, hidden when already saved), each with icon, name, description, address, ping, players and version; pinged on open, every 15 s and with Refresh. Icons are cached in `Multiplayer/ServerIcons/<hash>.png`; servers without an icon show the game icon. `ServerInfoWindow` shows all details and edits name, address and port (or adds a LAN server to the list).
- **Transport:** LiteNetLib 1.3.1 behind `INetTransport` (`LiteNetTransport`). Connection key `Spacebox:<Application.Version>`. Peer 1 is always the server; clients get their id via `AssignPeerIdMessage`.
- **Messages:** structs implementing `INetMessage` (`Serialize`/`Deserialize` with `NetWriter`/`NetReader`), registered with `NetworkManager.Messages.Register<T>(handler)`; id = FNV hash of the type's full name. `SendToServer` on the server dispatches locally, so game code is the same for host and client.
- **Objects:** `NetworkSpawner.Register(prefabKey, create, destroy)`; the server calls `Spawn(key, ownerPeer, writeSpawnData)` and late joiners get all objects (`SendSpawnedObjectsTo`). `NetworkObject` + `NetworkBehaviour` components; `NetworkVariable<T>` (server- or owner-writable, replicated at `TickRate` = 20 Hz, full state in spawn messages); `[Rpc(RpcTarget.Server|Owner|Clients|ClientsExceptOwner|All)]` methods called with `SendRpc(nameof(...), args)`, arguments serialized by `NetSerializer` (primitives, strings, vectors, quaternions, enums, arrays, `INetSerializable`, custom `Register<T>`); clients may only call `Server` RPCs, by default only on objects they own. `NetworkTransform` syncs owner-driven position/rotation as one sequenced `TransformState` (sender time, position, rotation; resent every 0.5 s while idle) interpolated by `TransformInterpolator` on the sender's clock (offset tracks the lowest latency, so arrival jitter is ignored), with a hold snapshot after idle gaps and a snap on jumps over 20 blocks. The server relays owner variables with the delivery they were sent with (sequenced updates are not relayed as reliable).
- **Join:** `JoinRequestMessage` (name, skin, version) → server checks version and unique name → `JoinAcceptedMessage` (world name, seed, mod id, game mode, time, saved player JSON, GameSet hash and folder) → GameSet check/download (below) → client loads `LocalSpaceScene` in client mode → `ClientReadyMessage` → server sends existing objects and spawns the `astronaut` prefab owned by the client (`PlayerSpawnService`, `AstronautNetwork`: transform, flashlight, held item).
- **Players and saves:** remote players are saved as `players/<name>.json` in the world folder; the local player (singleplayer and host) always uses `localplayer.json`, independent of the nickname (fallback on load: `players/<nickname>.json`, then the legacy `player.json`). Multiplayer death messages in chat include the death reason. Remote clients send their serialized state every 10 s and when leaving (`PlayerDataMessage`); the server writes it. Clients never save the world; their scratch folder is `Multiplayer/<host>_<port>/<world>` (`ServerFolderName`, the same key as the downloaded GameSet in `Server/<host>_<port>/GameSet`, so servers with the same name never share files). Console commands: `CommandBase.AvailableInTerminal` (default true) marks commands that work without a local player and window; the headless server does not register the others, so `help` lists only usable ones. Server terminal commands: `help`, `clear` (also clears the terminal), `version`, `color`, `resources`, `savelog`, `say`, `players`, `kick`, `ban`, `unban`, `unregister`, `mute`, `unmute`, `save`, `stop`, `restart`, `gm <0|1|2> <player>`, `tp <player> <x> <y> <z>`, `tpp <player> <target>` (owner RPCs on `AstronautNetwork`), `mob <id> <count> <player> | list | clear`.
- **World:** clients generate untouched asteroids from the seed and ask the server for saved/modified entity data (`EntityDataRequestMessage` → `EntityDataMessage`, NBT gzip bytes from the loaded entity, cache or file). Block edits are applied locally and sent as `BlockEditMessage`; the server applies and rebroadcasts them. When the server's cell differs from the request (rejected placement) or the edit overwrote another block (two players on one cell), the server sends the sender a correcting `BlockEditMessage` with its actual cell. After `EntityDataMessage` the server also sends the entity's current block states (`BlockStateNetwork.SendEntityStatesTo`). A rejected placement also sends the sender a `BlockPlaceRefundMessage`, which gives the block item back in survival (`PlacementRefund`). Partial block damage (drill ticks, authoritative projectiles) is sent as `BlockDamageMessage` (entity, cell, block id, damage) and subtracted on every peer (`BlockDamage.Apply`); removals stay normal block edits. Chat goes through the server (`ChatService`).
- **Server world range:** the server streams the world around every player, not only its own camera. `NetworkSession` feeds remote player positions into `WorldObservers`; `World` loads their sectors and keeps sectors near any observer, `Sector` generates asteroids within 300 blocks of each observer and unloads an asteroid only when it is far from the camera and all observers, `Asteroid` generates chunks within 128 blocks of each observer. Projectiles raycast the sector they are in (`World.SectorAt`). Clients re-send a container open request every second until the server has the container loaded.
- **Drops:** the server owns all drops (`DropManager.Replicator` = `DropNetwork`). Every drop has a network id; the server broadcasts spawn, quantity (merges) and removal (pickup, expiry) and sends all drops to late joiners. Remote clients never create drops: thrown items and destroyed storages send `DropSpawnRequestMessage`, block drops come from the server's own block removal. Pickup is claimed with `DropPickupRequestMessage`; the first valid claim (pickup delay passed, claimer within 6 blocks) gets `DropPickupGrantedMessage`, leftovers that do not fit are dropped again. Drop movement is simulated locally on every machine.
- **Combat:** `CombatNetwork.FireLocal` (called by `InteractionShoot`) spawns the shooter's projectile at once. On the server it is authoritative and is broadcast as `ProjectileSpawnMessage`; on a client it is cosmetic and `WeaponFireMessage` goes to the server, which checks fire rate and origin, spawns the authoritative projectile, fast-forwards it by the shooter's latency and broadcasts it to the others (fast-forwarded by the message age plus their own latency, shot sound at the shooter). Projectiles test their whole step segment (`Projectile.Step`), so fast shots cannot tunnel. Player hit detection uses `PlayerHitboxes` (head sphere and body capsule along the astronaut's up axis, headshots ×2 damage) with lag compensation: the server keeps 1 s of player state history and rewinds targets by the shooter's latency + `NetworkTransform.InterpolationDelay` (0.1 s, max 0.4 s). Only authoritative projectiles deal damage and break blocks (broken blocks are broadcast); cosmetic ones only play effects. Remote players hold blocks with custom shapes or several cells as their real model, scaled down to one block if bigger (`HeldBlockMesh`). Right click (`use`/`block_place`) with any item while looking at another player within 2 blocks gives one of it to them, checked in `InteractionHandler` before the held item's interaction (`ItemGiftNetwork` + `AstronautNetwork` RPCs: giver → server (distance, item and alive checks) → target owner applies it with `ItemReceiver`: equipment goes into its slot if empty, heal/power/oxygen consumables are applied, everything else goes into the hotbar/inventory → result back to the giver; in survival the item is taken at once and returned on failure or after 5 s without an answer). Remote players' held items animate: `AstronautNetwork` syncs an owner-written "using item" flag (drill held and animating) that makes the hand item vibrate, and every received shot (`ProjectileSpawnMessage`, or `WeaponFireMessage` on the server) kicks the shooter's gun back (`HandItemVisualizer.PlayKick`). Remote players have a kinematic solid `SphereBody` (radius 0.4, disabled while dead), so players and mobs collide with them; drilling a remote player sends its damage through `AstronautNetwork.DrillDamage` (server RPC, attacker within 8 blocks, max 20 damage per second per attacker) to `CombatNetwork.ApplyPlayerHit`. Damage goes to the victim (`PlayerDamageMessage`), the shooter gets `HitConfirmMessage` (`HitMarkerUI`). Remote players use snapshot interpolation (`NetworkTransform`, fixed 0.1 s delay).
- **Containers:** blocks with items implement `IContainerBlock` (storages, crusher/furnace/disassembler, oxygen generator, DNA reconstructor): window id, storages, extra state (`WriteContainerState`: name, processing progress, water tank) and a server hook after remote changes. Opening one on a remote client (`ContainerNetwork.OnInteract`) subscribes it on the server (`ContainerServer`), which sends a snapshot (all slots + state + version) and pushes a new snapshot whenever the storages change or the state changes (checked every 0.25 s). The client edits its local copy immediately; `ContainerClient` turns each change into `ContainerChangeMessage` (desired layout, per-item deltas, base version). If the base version matches, the server takes the layout after validating it (stack sizes, slot filters, totals = deltas); otherwise it merges: removals only up to what exists, additions only what fits. The result lists denied removals (taken back from the player) and rejected additions (returned to the player, dropped if full); then the client copy snaps to the server snapshot. While a change is pending, other containers and dropping items wait, and items can never be dropped straight from a container slot on a remote client. Machine processing, oxygen tank filling and DNA use run only on the server (DNA via `ContainerTakeRequestMessage`); breaking a container drops its contents on the server only. Renaming a storage goes through the server (`StorageNameNetwork`, max 32 characters) and is broadcast to every player.
- **Block state:** blocks implementing `INetworkStateBlock` call `BlockStateNetwork.MarkDirty(entity, cell, block)` on the server when their state changes; the state is broadcast to all players once per frame (`BlockStateMessage`), and sent to a client together with entity data when it loads the entity. Used for processing machines (running state, which drives the on/off textures), the oxygen generator water level (so clients compute the same air) and gravity generator settings (clients request changes with `GravityConfigMessage`). Electricity is computed by every machine from the same blocks and rates, so it stays identical; the only variable consumer (gravity generator) is synced through block state.
- **Doors:** clients send `DoorToggleRequestMessage`; the server toggles, `DoorSystem.StateChanged` broadcasts `DoorStateMessage` (entity, home cell, open) and every client plays the same animation (queued if one is running). Auto-close runs only on the server.
- **Explosions:** the server explodes bombs and broadcasts `ExplosionMessage` (bomb cell, bomb block id, exact destroyed cells as relative offsets). Clients replay it without drops (drops come from the server), with effects, and push/damage only their own player.
- **Container windows** close for everyone as soon as the container block is removed.
- **Death:** `AstronautNetwork` replicates `IsAlive` (owner-writable). On death the owner reports the last attacker (within 10 s) via a server RPC and the server posts the kill message in chat; dead remote players are hidden and tagged "(dead)" until they respawn.
- **GameSet download:** the server hashes its GameSet (`GameSetFolders.ComputeHash`: SHA-256 over every file of the mod folder plus `Default` when the mod is not `Default`, via `DirectoryArchive`) and sends the hash on join. The client uses its local GameSet with the same mod id if the hash matches, else a cached copy in `Server/<host>_<port>/GameSet/` if that matches, else it downloads the zipped GameSet (`GameSetPackage`, transfer name `gameset`) and extracts it there. Downloaded GameSets never go into `GameSets/`; the scene loads them with `SpaceSceneArgs.SearchForGameSetInLocalFolder = false` and `gameSetServerFolder`. Progress is shown in the join status.
- **Transfers (engine):** `NetworkManager.Transfers` sends large blobs in 32 KB chunks (16 per frame per transfer). The server registers providers with `Serve(name, provider)`; clients call `Request(name, completed, failed, progress)`. Max 512 MB; pending requests fail on disconnect.
- **Sectors and entities:** when a client loads a sector it requests a manifest (`SectorManifestRequestMessage`); the server answers once it has the sector loaded with the suppressed (destroyed) procedural ids and all player-built entities (id, file name, position). The client removes destroyed asteroids and registers the player-built ones, whose data then comes through `EntitySync`. Entities destroyed permanently on the server are broadcast (`EntityRemovedMessage`). Placing a block in empty space on a client sends `EntityCreateRequestMessage`; the server creates the entity and broadcasts `EntityCreatedMessage` (id, position, first block) to everyone.
- **Spacer:** spawned only by the server as the `spacer` network prefab (`Network/Npc/`). The server simulates physics, health and loot; clients get a kinematic replica moved by `SpacerNetwork` (a `NetworkTransform`). Client drill damage and pushes go to the server by RPC; damage effects are broadcast. Its storage is a container with an object key (`ContainerKey.ForObject(netId)`, resolved through the spawner), so loot uses the normal container sync; killing it drops the loot on the server and despawns it.
- **Mobs:** network prefab `mob` (`Network/Mobs/`, spawn data: mob id, position, timid flag, seed). The server runs AI and physics; `MobNetwork` (a `NetworkTransform`) moves kinematic replicas and replicates the current `MobAction` (chewing animation). Bites, eating particles, hurt and death effects are client RPCs; only the bitten player applies the damage (survival only). Player vulnerability (alive + survival) is an owner-written `AstronautNetwork` variable used for targeting. Drill damage and pushes from clients go to the server by RPC. Eaten blocks are removed on the server and broadcast as normal block edits. Spawner items send `MobSpawnRequestMessage` (checked: item type, distance ≤ 8 from the player, rate limit).
- **Players and moderation:** the server sends `PlayerListMessage` (peer, name, round-trip ping, muted, host) every second and on join/leave (`PlayerListNetwork`); the pause menu shows it in multiplayer (`PlayerListUI`). The host gets Kick, Mute and Ban buttons; the dedicated console has `kick`, `ban`, `unban`, `mute`, `unmute`. `ServerModeration` stores banned names, banned non-loopback IPs and muted names in `moderation.json` in the world folder; banned players are rejected on join, muted players' chat is dropped. Kicks and bans send the reason with the disconnect.
- **Connection feedback:** `ClientConnector` raises `StepAdded`/`ProgressChanged` for every join step; `ConnectionScreen` (drawn by `MenuScene` over the skybox) lists them, shows the GameSet download bar and errors in red with "Back to menu". Disconnects in game (`NetworkSession`) load the menu and show the reason (`DisconnectReasons.Describe` turns transport codes into text).
- **Time:** the server sends `TimeSyncMessage` to a joining client and every 10 s; clients snap when they drift more than 40 ticks.
- **Ore scanner (analyzer):** server-authoritative. Clients send `AnalyzerActionMessage` (start, cancel, clear); the server runs the scan (`AnalyzerScanner`, all analyzers in `AnalyzerRegistry` are updated every frame by `AnalyzerNetwork.Update`, so scans finish with the window closed), computes the mass and estimated minerals and broadcasts the state as block state (scanning, elapsed and total ticks, result). Power loss cancels the scan on every machine. The scan duration is saved (`duration_ticks`, optional).
- **DNA reconstructor:** the DNA count is block state, so clients see whether respawn is possible without opening it.
- **Ships** (`ShipNetwork`): pilots send `ShipCommandMessage` (sequenced: buttons, flight flags, aim) and `ShipMountMessage`; the server keeps one pilot per peer, simulates every ship and broadcasts `ShipStateMessage` (pose, velocities, console commands) every tick while ships move; clients interpolate 0.1 s behind (`ShipSnapshotBuffer`). Binding changes go through `ShipBindingRequestMessage` (cycle, camera, key) and are broadcast as `ShipBindingsMessage`; cannon shots as `ShipShotMessage`. A disconnecting peer leaves its seat.
- **Not synced yet:** other physics bodies (none besides the spacer, mobs and the player exist); no LAN discovery yet. Remote players in a sector other than the host's still use the host sector for drop and physics collisions.

## 9. Build, Test & Distribution

```bash
dotnet build Spacebox.sln
dotnet run --project Spacebox/Spacebox.csproj
dotnet test Spacebox.Tests [--filter "FullyQualifiedName~<Class>"]
dotnet run -c Debug --project Spacebox.Benchmarks
dotnet publish Spacebox/Spacebox.csproj -c Release -r <win-x64|linux-x64|osx-x64> --self-contained true --output ./publish
```

- `Resources/`, `GameSets/`, `Plugins/` and shaders are copied to the output folder as content files.
- `Release` and `Final` publishes with a runtime id are single-file: all managed and native libraries are bundled into `Spacebox(.exe)` (native libraries are extracted to the .NET bundle cache on first start), so the game folder holds only the executable, `Resources/`, `GameSets/`, `Plugins/`, the server scripts and runtime data. `--self-contained true` also bundles the .NET runtime; `--no-self-contained` (used by `Build/BuildWindows.ps1`) needs the installed .NET 8 runtime. Windows publishes bundle `Build/AddAfterBuild/OpenAL32.dll`. Content items are `ExcludeFromSingleFile` (they must stay files); `Release`/`Final` builds embed their pdbs (`Directory.Build.props`). On Linux, OpenAL comes from the system (`libopenal`).
- Packaging: `Build/BuildWindows.ps1` (`$selfContained` switch; the .NET installer zip is added only for framework-dependent builds) and `Build/BuildLinux.ps1` (self-contained linux-x64 zip). Both apply `Build/exclude.txt` and open the output folder. Launch scripts are platform-specific (`LaunchScripts` in `Spacebox.csproj`): Windows targets get `start-server.bat`, Linux/macOS targets get `start.sh` and `start-server.sh` (builds without a runtime id use the current OS). Publishes also contain a default `serverconfig.json` (`Spacebox/serverconfig.json`, empty `Seed` = random seed when the server world is created); normal builds don't copy it, the server creates it on first start.
- Linux: run `sh start.sh` (game) or `sh start-server.sh` (dedicated server); both set the executable bit lost in zips. The server needs a display for its hidden GL window: without `DISPLAY`/`WAYLAND_DISPLAY` the script uses `xvfb-run`. System packages: OpenAL (`libopenal1`), OpenGL 3.3 drivers, X11 or Wayland libraries, ICU (`libicu`). The game sets the working directory to its own folder at start, so relative resource paths work from any launcher.
- Tests cover packed vector types, blocks, atlas packing (`AtlasLayout`), AO, mesh generation, world logic and version conversion.
- API docs: Doxygen (`Doxyfile`, theme in `Documentation/doxygen-awesome-css`).
- Releases: https://pasterlak.itch.io/spacebox
