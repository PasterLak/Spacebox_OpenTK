Rules for DONE.txt

For the author: how to write future entries so the next changelog is quick to build.

  • One line per player-visible change. Split lines that list unrelated things.
  • Short: about 15 words at most, a phrase, not a sentence.
  • Final state, not history. Edit the existing line when a feature changes in the same version.
  • No "fix X" for new features. Bugs in a feature added this version are not entries.
  • Right header: Game for features, Small for minor changes, Fixes for bugs in released features, Engine for engine work.
  • Current version only. Add under Application.Version; never edit older sections.
  • No internal work: refactors, tests, tooling and docs stay out.
  • Player words: name items, blocks, keys and menus as the game shows them.
  • Exact names for config fields, rules and commands, e.g. keep_inventory, /backup.
  • No other games and no numbers that change often; keep values in tooltips and docs.
